# Changelog

Each entry records what changed and why.

## 2026-10-07 — Signal validity and band-pass sensitivity

### Sampling rate derived from the exported clocks
- **What:** `src/features/quality.py::sampling_rate_from_clock` estimates the rate as (samples − 1) / elapsed time for each record. All 88 records give 1,923.9–1,925.9 Hz (median 1,925.9 Hz), and `scripts/evaluate_bandpass.py` checks that they agree within 0.2% before using one rate.
- **Why:** earlier documents treated the rate as unknown, so no filtering was possible. The rate was only checked on six clocks. Using all 88 clocks, the agreement and the match with the Delsys Trigno EMG rate (1,925.926 Hz) make it a data-derived estimate rather than a guess. Using only the first and last timestamps keeps the estimate valid for the patient clocks with more than 90% duplicate stamps. The duplicates turn out to be rounding, not missing samples.

### 20–450 Hz band-pass as an additional specification
- **What:** `scripts/evaluate_bandpass.py` applies a zero-phase 4th-order Butterworth 20–450 Hz band-pass and recomputes all 21 amplitude specifications (1,848 evaluations). Outputs: `reports/bandpass_*.csv`, `reports/bandpass_checks.json`, `reports/figures/bandpass_sensitivity.png` and `docs/history/bandpass_results.md`.
- **Why:** "the results were not filtered" is the first objection an EMG reviewer raises. With the rate known, it can be answered with data instead of a limitation statement. Result: 1 of 43 primary pairs changes whole-RMS direction (0.995 → 1.000) and no cohort median moves by more than 0.05. The exported baseline is kept unchanged, because the built-in Delsys preprocessing is undocumented and the band-pass is a sensitivity analysis, not a reconstruction.

### In-band energy share as a quality indicator
- **What:** `in_band_share` (band-passed RMS / mean-centered RMS) is reported for every record. Records below 0.8 are flagged `low_in_band_share`.
- **Why:** the earlier |mean|/RMS flag only detects DC offset. In-band share also detects drift and movement content, and it points to four specific control records (healthy9 iso90/iso180 uninv, healthy8 iso90 uninv, healthy3 iso180 uninv). The 0.8 cut-off was chosen after looking at the spectra, so it flags records for review and never excludes them.

### healthy8/iso90 excluded from the primary presentation
- **What:** `short_records` and `excluded_pairs` in `src/features/quality.py` implement the existing rule (record shorter than 25% of its cohort-condition median). Pairs meeting it are left out of the primary counts in `evaluate_robustness.py` and `evaluate_bandpass.py`. Only healthy8/iso90 qualifies. All 44 pairs remain in the sensitivity outputs, and the robustness matrix labels the excluded row.
- **Why:** its uninv record lasts 2.0 s; the next shortest of 88 lasts 10.5 s and its partner about 25 s. A whole-record ratio between a full task and a fragment does not measure limb asymmetry. Earlier documents attributed the extreme ratio (25.2) to a small denominator, but centering (46.5) and band-pass (64.6) make it larger, not smaller, so it cannot be a correction artefact. The rule already existed as a review flag; promoting it to an exclusion is retrospective and documented as such. The headline counts (13 and 10 crossings) are unchanged because this pair never crosses ratio 1.
- `exploratory_amplitude.py` now uses the same shared function, so the rule is defined in one place. Its outputs are byte-identical.

### Pipeline and delivery
- **What:** `run_all.py` now also runs `review_signals.py` and `evaluate_bandpass.py`. `prepare_kaggle.py` includes `evaluate_bandpass.py` in the notebook.
- **Why:** the signal-review figures were committed but not regenerated by the pipeline, so they could drift from the code. The Kaggle notebook should reproduce the same analyses as the repository.

### Tests
- **What:** three tests in `tests/test_core.py`. They check the clock rate with heavily rounded clocks, that the band-pass keeps a 100 Hz component and removes drift (in-band share matches the analytical value √(0.5/5)), and that the short-record rule excludes one pair, not the cohort.
- **Why:** every new rule that changes which numbers are reported needs a check with a known answer.

### Repository size
- **What:** signal-review figures saved at 100/110 dpi instead of 140/160 (about 3.3 MB → 2.1 MB). `reports/synthetic_scenario_results.csv` (23,100 rows, about 2 MB) is no longer versioned. It is regenerated by `simulate_measurement_scenarios.py`, and the summary CSV stays in Git.
- **Why:** these are generated files that dominate repository size without adding information a reader needs online. The figures remain legible.

### Documentation
- **What:** README, `review_methods.md`, `review_results.md`, `review_limitations.md`, `review_case.md` (now four figures), `data_dictionary.md` and the generated centering report were updated.
- **Why:** they stated that the sampling rate was unknown, that no band-pass was possible and that no pair was excluded, which is no longer true. The limitations now list every retrospective decision explicitly.

### Development environment
- **What:** README advises creating the virtual environment outside synced folders such as OneDrive.
- **Why:** a `.venv` inside OneDrive synchronizes thousands of package files. `.dev-tools/` (vendored pytest and ruff) was replaced by `requirements-verification.txt` in a normal virtual environment.
